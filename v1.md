# v1 — Multi-Agent, Multi-Chat, Local-First Bot Platform

**Status:** draft, expect iteration
**Owner:** caleb
**Scope:** the broader platform vision. The MCP scheduling shim is a component; see [`mcp-shim.md`](./mcp-shim.md) for that spec.

## 1. Vision

A bot platform whose *default* deployment is fully local and self-hosted:

- **Local LLM** (Ollama, llama.cpp, LM Studio, or similar) instead of a cloud model API.
- **Local agent runner** (Crush, or another local-first agent framework) instead of claude-code.
- **Local chat server** (Zulip on-prem, or Matrix) instead of Slack.
- **Local execution** — the same docker-per-session sandbox model we already have.

Along the way, the platform supports mixing and matching:

- Any supported chat frontend × any supported agent backend.
- Per-domain choice of backend — some domains stay on Anthropic + claude-code because they need top-tier reasoning; others run on Ollama + Crush because they mostly need code editing and don't want data leaving the box.
- Gradual migration — today's Slack + claude-code setup keeps working while new backends come online alongside.

The UX we've built stays intact: per-thread agent sessions, verbosity/model/effort controls, plan mode, permission dialogs, file uploads, permalink expansion, home tab help. Users shouldn't notice which backend a domain runs on unless they care.

## 2. Non-goals

- **No remote agent management APIs.** Anthropic Managed Agents, OpenAI Assistants API, and equivalents are explicitly off the table. The whole point is trending toward self-hosted; a cloud orchestration layer in the critical path defeats that.
- **No wholesale rewrite.** Everything gets refactored incrementally. The current bot keeps working throughout.
- **No proprietary chat platform as the long-term recommended default.** Slack support stays as long as it's where users are; the recommended deployment path shifts to Zulip/Matrix over time.
- **No custom agent-loop framework.** We use existing framework code (claude-code, crush, ...) and build the platform *around* them, not underneath.
- **No non-MCP interop layer.** MCP is the interop bet. Portable capabilities (scheduling, background jobs, chat-file transfers, etc.) live in MCP servers the bot owns.

## 4. Target architecture — four layers

```
┌─────────────────────────────────────────────────────────────────┐
│  Layer A — ChatAdapter                                          │
│    slack.Adapter, zulip.Adapter, matrix.Adapter, ...            │
│  (implements: post/edit/react/upload, interactive components,   │
│   home/help render, event stream)                               │
└─────────────────────────────┬───────────────────────────────────┘
                              │
┌─────────────────────────────▼───────────────────────────────────┐
│  Layer C — Bot Core                                             │
│  (chat-agnostic, agent-agnostic)                                │
│    session store, domain resolution, command parsing,           │
│    permission mediation policy, authorization,                  │
│    auto-name, progress model, verbosity/plan/filesync policy    │
└─────────────────────────────┬───────────────────────────────────┘
                              │
┌─────────────────────────────▼───────────────────────────────────┐
│  Layer B — AgentAdapter                                         │
│    claudecode.Adapter, crush.Adapter, ...                       │
│  (implements: start/resume/interrupt, configure, stream events, │
│   list capabilities)                                            │
└─────────────────────────────┬───────────────────────────────────┘
                              │
┌─────────────────────────────▼───────────────────────────────────┐
│  Layer D — Portable capabilities (MCP servers)                  │
│    scheduling (mcp-shim.md), background jobs,                   │
│    chat-file bridge, thread-permalink expansion, ...            │
│  (agent-independent; both claude-code and Crush consume via MCP)│
└─────────────────────────────────────────────────────────────────┘
```

**Layer A — `ChatAdapter`.** One per chat platform. Owns everything platform-specific: message send/edit/delete, reactions, interactive components (Block Kit / Zulip inline / Matrix widgets / fallback numbered-text), uploads, DM vs channel vs thread semantics, home-tab render. Emits a normalized event stream (`NewMessage`, `InteractiveCallback`, `DMOpened`, ...) that the bot core consumes.

**Layer B — `AgentAdapter`.** One per agent framework. Owns process launch, session resume, event decoding (Anthropic stream-json / Crush SSE / whatever's next), settings mediation (model/effort/plan), and native-tool discovery. Emits a normalized event stream (`TextDelta`, `ToolUseStart`, `ToolResult`, `Thinking`, `PermissionRequest`, `SessionEnd`, `Error`).

**Layer C — Bot Core.** Everything about "an agent runs on behalf of a chat user in a bounded workspace." Doesn't know or care which chat or which agent. This is where the current `sessions.go`, `domains.go`, `autoname.go`, `parser.go`, the command-parsing arm of `handlers.go`, and the permission-mediation policy live.

**Layer D — Portable capability MCPs.** The bot owns MCP servers that expose durable, cross-cutting capabilities to whatever agent's running. Scheduling (from `mcp-shim.md`) is the first; likely followed by background-job supervision, a chat-file bridge (so agents can upload results into the thread without knowing which chat), and possibly a thread-permalink expander. **These live above both A and B on the stack because they use both** — a cron tick may need to run a shell command (agent-adapter-free) and post a Slack/Zulip notice on failure (chat-adapter-free).

## 5. Interface sketches

Illustrative Go — real signatures shake out during phases B and D of §6.

```go
// -------- Layer A -------------------------------------------------------------

type ChatAdapter interface {
    Name() string
    Self(ctx context.Context) (BotID, error)

    // Message flow. ConvoKey is opaque — the adapter maps it to
    // (channel, thread_ts) / (stream, topic) / (room, thread_root) etc.
    Post(ctx context.Context, convo ConvoKey, msg Message) (MsgRef, error)
    Update(ctx context.Context, ref MsgRef, msg Message) error
    Delete(ctx context.Context, ref MsgRef) error

    AddReaction(ctx context.Context, ref MsgRef, emoji string) error
    RemoveReaction(ctx context.Context, ref MsgRef, emoji string) error

    // Interactive components — adapter chooses richest available
    // representation (Block Kit radio buttons vs numbered-reply parsing).
    AskChoice(ctx context.Context, convo ConvoKey, q Choice) (<-chan ChoiceResponse, error)
    OpenModal(ctx context.Context, ref MsgRef, spec Modal) (<-chan ModalSubmission, error)

    // File transfer
    Upload(ctx context.Context, convo ConvoKey, name string, r io.Reader) (FileRef, error)
    Download(ctx context.Context, ref FileRef) (io.ReadCloser, error)

    // Home / help — RenderHome may be a no-op on platforms without one;
    // help is then delivered inline as a message.
    RenderHome(ctx context.Context, user UserID, content HomeContent) error

    Events() <-chan ChatEvent

    Start(ctx context.Context) error
    Shutdown(ctx context.Context) error
}

// -------- Layer B -------------------------------------------------------------

type AgentAdapter interface {
    Name() string // "claude-code", "crush", ...

    Start(ctx context.Context, spec SessionSpec) (Session, error)
    Resume(ctx context.Context, sessionID string, spec SessionSpec) (Session, error)

    // Which capabilities does this adapter's underlying agent framework
    // support natively? Bot core uses this to decide whether to advertise
    // a portable-MCP alternative.
    Capabilities() AgentCapabilities
}

type Session interface {
    ID() string
    Stdin() io.Writer
    Events() <-chan AgentEvent
    Interrupt(ctx context.Context) error
    Configure(ctx context.Context, s Setting) error
    Wait() error
}

type SessionSpec struct {
    CWD               string
    Model             string
    Effort            string
    PlanMode          bool
    Verbosity         int
    MCPServers        []MCPServerSpec // portable capabilities (scheduling, etc.) plumbed here
    SystemPromptFiles []string
}

type AgentCapabilities struct {
    NativeScheduling      bool // claude-code: yes (but broken for us). crush: no.
    NativeBackgroundBash  bool
    NativeSubagents       bool
    InputFormat           string // "stream-json", "text", ...
    ResumeMechanism       string // "session-id-flag", "sqlite-db", ...
}

type AgentEvent interface{ isAgentEvent() }
// Concrete: TextDelta, ToolUseStart, ToolResult, Thinking,
// PermissionRequest, SessionEnd, Error

// -------- Layer C -------------------------------------------------------------

// Bot Core doesn't have an interface — it's the composition root.
// It owns: session store, domain registry, command parser, permission
// mediation policy, authorization, auto-namer, and the routing loop
// that wires ChatAdapter events → agent turns and AgentAdapter events
// → chat renders.
```

## 6. Migration path

Each phase is small, ships independently, and doesn't break what shipped before.

**Phase A — Portable capability MCPs.**
Ship the MCP scheduling shim per `mcp-shim.md`. Kills the eagle failure now. Establishes the pattern for future capability shims (background jobs, chat bridges). No adapter refactor required.

**Phase B — Extract `AgentAdapter`.**
Move `runner.go` and claude-facing parts of `permission.go` into `bot/agent/claudecode/`. No behavior change; just code motion behind a stable interface. Only doable after phase A because the MCP servers plug in via `SessionSpec.MCPServers`, so the interface has to know about MCP config.

**Phase C — Add `crush` adapter.**
Prerequisite: a headless-mode subcommand in Crush (upstream PR or fork). Once that's real, `bot/agent/crush/` wraps it, wires its `crush.json` MCP section to our portable-capability shims, and points at a local Ollama container. The domain-init flow gains a "backend: claude | crush" question.

**Phase D — Extract `ChatAdapter`.**
Move `bot.go`, `askuserquestion.go`, `hometab.go`, and Slack-facing parts of `handlers.go` and `files.go` and `permission.go` into `bot/chat/slack/`. Same pattern as phase B: no behavior change.

**Phase E — Add `zulip` adapter.**
`bot/chat/zulip/`. Slack Block Kit → Zulip Markdown + inline replies. Interactive components fall back to numbered-reply parsing where Zulip doesn't have a rich equivalent. Home tab equivalent = a bot-owned stream+topic that renders the same help content.

**Phase F — Local-first defaults.**
Default domain template uses Crush + a local Ollama container (with a sane starter model — probably `qwen3-coder:30b` given eagle's existing config). Documentation shifts to show self-hosted (Zulip + Crush + Ollama) as the primary deployment path. Cloud API keys become an optional feature for domains that need frontier reasoning.

Anywhere between phases users get a working bot with strictly more backends available.

## 7. Design tensions and trade-offs

- **Interactive-component fidelity varies.** Slack Block Kit is rich; Zulip is Markdown + minimal buttons; Matrix has widgets but client support is uneven. The common denominator is *"post options as numbered text, parse the user's next reply as the choice."* Each adapter opts into richer components where available; core code shouldn't assume any specific richness.
- **Agent capabilities vary.** claude-code has `TaskCreate`, structured `AskUserQuestion`, native subagents. Crush has neither cron-equivalents nor (as of writing) a documented headless mode. Portable capabilities via MCP shims MUST work everywhere; agent-native ones are best-effort and the bot never *requires* them.
- **Local LLMs are less capable.** `qwen3-coder:30b` is not `claude-opus-4-8`. Domains needing top-tier reasoning stay on the cloud model even post-migration; the goal is that self-hosting is a real option, not that everyone flips overnight.
- **Docker orchestration per adapter.** claude-code runs in a docker container for isolation. Crush would too. A hypothetical "shell adapter" (direct on host, no isolation) would need the AgentAdapter abstraction to allow bypassing docker. Design for it.
- **Session identity across restarts.** claude-code has a session UUID we pass to `--resume`. Crush uses a SQLite file. Zulip vs Slack thread IDs differ. The bot core's session store keys by `(chat_adapter_id, convo_key)` and stores the agent-adapter-specific resume token alongside.
- **Per-domain backend selection.** A user's `services` domain might be on claude+Slack; their `random` domain on crush+ollama+Zulip. Session store records `{chat_adapter, agent_adapter, cwd, resume_token}` per session.

## 8. Portable capabilities — the MCP shim family

The scheduling shim (`mcp-shim.md`) is the first. Others we'll likely want as adapters proliferate:

- **Scheduling** (`cron_*`, `bg_*`) — mcp-shim.md. Fixes eagle.
- **Chat-file bridge** — canonical `upload_to_chat(file, description)` tool the agent calls without knowing which chat platform. Adapter renders (Slack file share vs Zulip attachment vs Matrix media upload).
- **Thread-permalink expander** — takes a Slack/Zulip/Matrix permalink, resolves it to text (with cross-platform normalization), and returns it as tool result. Removes chat-specific permalink parsing from agent-adapter code.
- **Permission mediation** — the existing permbridge fits this shape. Could get generalized so its policy (ask? auto-approve? which chat UI to use?) lives in bot core, not in the agent adapter.
- **State-file cache** — a portable "read/write a scratch file that survives container restarts" utility. Reduces the ceremony of state-file workflows the model already learned.

Each is an MCP server binary the bot owns, embedded into the bot binary, deployed into the per-session runtime dir, listed in the agent's MCP config. Same pattern as `permbridge` and the upcoming `schedbridge`. Adding a new capability doesn't require touching any adapter.

## 9. Deliberately deferred (or never)

- **Non-MCP interop.** Only MCP. If a future agent framework doesn't speak MCP, we don't add first-class support for it.
- **Custom agent loop.** Never. Use the framework's loop.
- **Cloud LLM proxies as a primary feature.** OK as an intermediate step (bot points at Anthropic API today), but the local-first target is the north star.
- **Managed cloud chat platforms as a long-term default.** Slack stays supported for users who want it; the recommended deployment doesn't require any cloud account.
- **Plugin loading (Go plugins, .so files).** All adapters compiled in. Simpler to reason about; matches the deployment model (one bot binary per host).
- **A single unified schema across chat platforms for interactive components.** Least-common-denominator + adapter opt-in for richer forms is simpler than trying to enforce a schema that every platform must implement.

## 10. Open questions

1. **Adapter selection: per-domain or per-session?** Recording backend in `.clod/config` per domain is simpler; a `@bot switch backend` command is more flexible but complicates session store.
2. **Local-LLM defaults: where do they ship?** In the bot's default `NewDomain` template (opinionated), or as a separate template pack users opt into (neutral)?
3. **Cross-chat authorization.** Slack keys users by `U08...`, Zulip by email, Matrix by MXID. Do we key core auth by chat-native ID (adapter-scoped user lists), or introduce an internal user ID with per-backend bindings? The latter is cleaner but adds a whole identity-management surface.
4. **`AgentEvent` shape.** Strongly typed union (one Go type per event kind, `isAgentEvent()` sealed interface) or a single struct with a discriminator field? First is more idiomatic Go, second is easier to add new event types without touching every adapter.
5. **Portable-capability socket topology.** One socket per agent session (matches current per-session `permbridge` FIFO), one socket shared across all agent sessions on the same bot, or one socket per capability regardless of session? First is the current pattern and easiest; last is closer to how "system daemons" would look.
6. **Crush the only local target, or design for a family?** Do we build the AgentAdapter interface with only Crush in mind, or plan for opencode / aider / continue / etc. as future adapters from day one? Cost of the latter is small at design time but shapes what we call `AgentCapabilities`.
7. **Config surface.** A single `clod.yaml` at the bot's config root declaring adapters and defaults? Or per-adapter config sections in a shared file? Or completely env-var-driven? Current bot leans env-var-driven; a proper config file is probably where this ends up.
8. **How does `ChatAdapter` handle DMs vs channels vs threads?** All map to `ConvoKey` in the sketch above, but the *semantics* differ: DMs are 1:1, channels are broadcast, threads are conversational nesting. Does the core need to know which is which (for permission gating, e.g. "commands only work in DMs")? Probably yes — the `ConvoKey` should carry a `Kind` alongside its opaque platform ID.
9. **Cutover strategy for local-first.** When a user upgrades the bot after phase F, do their existing domains stay on claude+Slack? Only new domains default to local? Or do we prompt users to migrate? Probably: existing stays, new defaults to local, migration is manual and documented.
10. **Portable-capability *rendering* through the chat adapter.** When a cron fires with a non-zero exit and we want to post a notice, does the scheduling shim call `Post` on the chat adapter directly (Layer D → Layer A), or route via bot core (Layer D → Layer C → Layer A)? Latter is cleaner but adds indirection.

## 11. Not answered yet — needs a spike

- Detailed threading model for `SessionSpec` and event types (finalizes during phase B when we have one adapter that has to satisfy the interface).
- What "session" means in Crush vs claude terms — different SQLite-per-project vs Anthropic-session-id.
- How agent-native features that don't map cleanly are handled (e.g., claude's `--include-partial-messages` has no Crush equivalent; do we drop the feature at that adapter boundary, or synthesize partial messages from Crush's SSE stream?).
- Whether the local-LLM container image ships with the bot's docker templates or is user-provided.
- Where the seam is between "bot core does it" and "chat adapter renders it" for verbosity/model indicators (currently emoji reactions on the anchor message — does every chat platform have reactions? Zulip has emoji reactions, Matrix does, Discord does, but the interaction model varies).
- Whether to keep the current single-binary deployment model or split into a bot core + separately-deployable adapter binaries (probably keep single binary; simpler to operate).
- Test strategy for multi-adapter combinations. Combinatorial matrix could get large; hopefully most tests can pin one adapter and mock the other.

## 12. Relationship to `mcp-shim.md`

`mcp-shim.md` is the concrete v0 deliverable — Layer D's first capability, shippable independently of any adapter refactor. It stands alone; it does not depend on this v1 plan being executed. If the v1 refactor is pursued, `mcp-shim.md`'s design fits it cleanly (portable capabilities are Layer D). If v1 is deferred or reshaped, `mcp-shim.md` still solves the eagle failure and is worth shipping on its own merits.

The scheduling shim is also the forcing function for figuring out where portable-capability MCP servers *live* in the architecture — if we get the pattern right for scheduling, background jobs and chat-bridge shims fall out of the same template.
